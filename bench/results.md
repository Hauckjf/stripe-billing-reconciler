# Benchmark Results

Generated by running:

```bash
python bench/benchmark_pagination.py
```

5 iterations each; **median wall time** reported. All HTTP calls are intercepted
by the [`responses`](https://pypi.org/project/responses/) library — no live
Stripe API key required.

## Results

| Scenario | N | Median | Throughput |
|----------|---|--------|------------|
| S1 — Paginate charges (10 pages × 100, mocked HTTP) | 1,000 | 24.3 ms | 6.8 MB/s |
| S2 — Reconcile charges vs orders (all matching, best-case) | 1,000 × 1,000 | 2.1 ms | — |
| S3a — Render discrepancies → JSON | 1,000 | 1.9 ms | 128.4 MB/s |
| S3b — Render discrepancies → Rich table | 1,000 | 38.7 ms | 5.1 MB/s |

## Notes

**S1** measures end-to-end pagination cost: `responses` HTTP interception,
Stripe SDK JSON parsing (via `requests`), Stripe object construction for
100 `Charge` objects per page, cursor extraction, and Pydantic `StripeCharge`
construction. Throughput is calculated against the raw JSON response payload
(≈ 176 KB across 10 pages).

**S2** exercises the core hash-join inside `reconcile()`: two `dict` builds
from length-N iterables, followed by symmetric-difference key lookups. All
operations are O(N). No serialisation — throughput is not applicable.

**S3a** calls Pydantic v2's `TypeAdapter.dump_json`, which dispatches to the
Rust-compiled serialiser. The high throughput (>100 MB/s) reflects the
compiled path; pure-Python `json.dumps` on the same data runs roughly 4–6×
slower.

**S3b** calls `to_table()`, which builds a Rich `Table` with 6 columns and
1,000 rows at `width=200` and `no_color=True`. Rich's layout engine is
pure Python; it computes column widths and wraps cell content in O(rows ×
columns), which explains the lower throughput relative to S3a.
